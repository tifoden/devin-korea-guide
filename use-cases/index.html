공식 고객 사례로 본 Devin 활용

Cognition이 공식 사이트에 공개한 고객 사례 여덟 건을 업무 유형별로 묶었습니다. 수치는 각 사례 페이지에 적힌 그대로 옮겼습니다.

이 페이지의 사례는 모두 Cognition이 공식 고객 사례 페이지에 공개한 것입니다. 이 가이드가 따로 취재하거나 검증한 결과가 아니고, 수치는 각 회사의 환경에서 나온 값이라 다른 팀에서도 똑같이 나온다는 뜻이 아닙니다.

이 페이지를 읽는 법

  • 표시 없는 본문은 공식 사례 페이지를 요약했고, 수치는 원문 표현을 그대로 옮겼습니다.
  • 필자 제안은 공식 자료에 없는 필자의 의견입니다.
  • 가상 실습은 설명용으로 지어낸 예제로, 실제 사례가 아닙니다.

장애 대응과 인시던트 조사

회사 공식 사례에 적힌 내용 원문 표현
AngelList 엔지니어가 들어오기 전 1차 조사에서 근본 원인을 찾은 인시던트 비율이 자체 제작 에이전트를 쓸 때 20%에서 Devin으로 70%가 되었다고 밝힙니다. “from 20% to 70%”
Modal 인시던트의 약 80%에서 Devin이 정확한 원인이나 엔지니어가 다듬을 수 있는 가설 같은 유용한 결과를 낸다고 밝힙니다. 세션 기록은 Slack 스레드에 남습니다. “On roughly 80% of incidents, Devin produces something useful”
근거

AngelList, Modal

버그 수정과 일상 개발

회사 공식 사례에 적힌 내용 원문 표현
Finch Legal PR 약 3,000개를 병합했고, 이는 엔지니어링 시간 약 20개월에 해당한다고 밝힙니다. Slack 요청을 Devin이 분류하고 Linear 티켓을 만든 뒤 로그로 조사합니다. “merged around 3,000 PRs, roughly 20 months of engineering time”
Gumroad Devin이 병합된 PR 1,500개 이상으로 회사의 1위 기여자가 되었고, 하루 약 10개의 PR이 병합된다고 밝힙니다. “1,500+ Merged PRs … ~10 PRs merged by Devin daily”
Linktree 지난 한 달 동안 Devin이 PR 약 300개를 작성해 약 100개가 병합되었고, 대부분 고객이 보고한 버그 수정과 작은 기능 구현이었다고 밝힙니다. “Over the past month Devin has authored ~300 PRs and merged ~100”
Ramp Devin에 익숙한 소수의 엔지니어가 주당 최대 80개의 병합 PR을 담당했다고 밝힙니다. 기술 부채 정리, feature flag 제거 같은 작업이 예로 나옵니다. “up to weekly 80 merged PRs”
근거

Finch Legal, Gumroad, Linktree, Ramp

대규모 마이그레이션

회사 공식 사례에 적힌 내용 원문 표현
Nubank 수백만 줄 규모의 핵심 ETL 모놀리스를 하위 모듈로 옮기는 작업에서 8–12배 빠른 마이그레이션과 20배 낮은 비용을 얻었다고 밝힙니다. “8-12x faster migration … slashing migration costs by 20x”
Itaú 서비스 59개의 .NET→Java 마이그레이션과 데이터베이스 객체 800개의 SQL Server 마이그레이션을 더 빨리 마쳤고, 테스트 커버리지가 약 50%에서 약 90% 이상으로 올랐다고 밝힙니다. “59 services … 800 database objects … from ~50% to ~90+%”
근거

Nubank, Itaú

공식 문서가 소개하는 작업 유형

공식 문서에는 고객 사례와 별도로 Devin에게 맡기기 좋은 작업 유형별 안내가 있습니다. Java 버전 업그레이드, COBOL 현대화, 엔지니어링 백로그 정리, SAS에서 PySpark로, JavaScript에서 TypeScript로, NoSQL에서 SQL로의 마이그레이션, API 연동, 테스트 커버리지 보강, 컨테이너화 등입니다.

기능을 조합해 쓰는 장면

위 고객 사례와 별개로, 공식 문서가 직접 설명하는 사용 흐름을 기능 조합별로 정리했습니다. 특정 고객의 결과가 아니며 수치도 없습니다. 기능별 조건과 제약은 기능 페이지에 있습니다.

장면 함께 쓰는 기능 공식 문서가 설명하는 흐름
모바일 앱 변경 확인 Android 에뮬레이터, macOS VM의 iOS Simulator, 테스트 녹화 Android는 PR마다 앱을 에뮬레이터에서 실행해 주요 흐름을 눌러 보고 녹화를 남기는 흐름을 소개합니다(“You get a video recording that proves the feature works”). iOS·macOS 앱은 블루프린트에 runs-on: macos를 지정해 빌드·테스트합니다.
로컬에서 계획, 클라우드에서 구현 Devin CLI /handoff, Agent Command Center CLI가 대화 맥락과 현재 git 브랜치를 묶어 클라우드 세션을 만들고, 그 세션의 PR을 다시 로컬로 가져올 수 있습니다.
커밋 전 이중 확인 Quick Review, Since last seen 보기 로컬 변경을 별도 에이전트가 검토하고, 다시 볼 때는 마지막으로 본 뒤 바뀐 부분만 확인합니다.
팀 절차를 매번 같게 Skills, 환경 스냅샷 테스트·배포 절차를 SKILL.md로 남기고, 승인한 블루프린트로 만든 스냅샷에서 세션을 시작합니다. 개인 Memory는 팀과 공유되지 않으니 팀 규칙은 스킬로 둡니다.
여러 저장소 점검 Code Scans, Automations, Dynamic Workflows /scan으로 문제 유형을 찾고, 새 커밋만 다시 스캔하거나 일정으로 돌립니다. 독립된 작업이 많으면 워크플로로 나눠 처리한 뒤 결과를 합칩니다.

큰 작업을 조각으로 나눠 맡기기

위 마이그레이션 사례처럼 큰 일을 Devin에게 맡길 때 공식 문서가 강조하는 건 ‘한 번에 크게’가 아니라 ‘작게 나눠 여러 번’입니다. 복잡한 새 기능을 깊게 파고드는 일(Tall & Deep)은 규모가 커질수록 신뢰도가 떨어지고, 단순하고 정의가 분명한 작업을 넓게 반복하는 일(Wide & Shallow)이 안정적이라고 설명합니다.

기준 공식 문서의 설명
조각 크기 파일, 노트북, 모듈처럼 가장 작은 단위로 나눕니다. 각 조각은 사람이 직접 하면 90분 미만인 일이어야 합니다(“under 90 minutes of manual engineering work”).
검증 수단 테스트, 빌드, CI, 직접 만든 검증 스크립트처럼 성공과 실패를 분명히 가르는 수단이 있어야 합니다.
독립성 조각끼리 서로 기다리지 않고, 하나만 병합해도 기존 동작이 깨지지 않아야(하위 호환) 동시에 돌릴 수 있습니다.
사람 검토 조각이 끝날 때마다 사람이 검토한 뒤 main에 병합합니다.
오류 누적 수천 개 조각으로 늘리면 작은 오류율도 쌓인다고 경고합니다.

맞는 일로는 마이그레이션, 리팩터링, 현대화, 기술 부채 백로그를 꼽습니다. 반대로 외부 시스템이나 의존성이 많이 얽힌 일은 피하라고 권합니다. 첫 세션용 작업 고르는 법은 첫 작업 시작하기에, 여러 세션을 동시에 돌리는 기능은 Devin Cloud 페이지에 정리했습니다.

가상 실습: 우리 팀에 맞는 첫 사례 찾기

가상 실습

팀과 수치 모두 설명을 위해 지어낸 것입니다

가상의 10명 규모 개발팀이 매주 Slack으로 들어오는 작은 버그 신고를 처리하느라 계획한 작업을 미룬다고 가정합니다. 위 사례 중 Finch Legal과 Linktree처럼 ‘작고 반복되는 버그 수정’ 유형에 해당합니다. 이 팀은 지난 2주 동안 들어온 버그 신고 중 재현 방법이 분명한 것 다섯 건을 골라 Devin에게 하나씩 맡기고, 병합된 PR 수와 리뷰에 든 시간을 직접 기록해 비교해 볼 수 있습니다.

필자 제안

숫자보다 유형을 보기

사례의 수치는 회사마다 조건이 달라 그대로 비교하기 어렵습니다. 우리 팀의 일과 같은 유형의 사례를 찾고, 작은 시범 작업으로 직접 측정하는 편이 판단에 더 도움이 됩니다.
